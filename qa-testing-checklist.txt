2. FORM VALIDATION & BOUNDARY CASES
=============================================================================
[ ]    Required-field validation on every form (some spot-checked, not

[ ]    Invalid formats: malformed email, garbage URLs in website/logo
       fields, invalid image URLs
[ ]    Boundary values: very long photographer names/descriptions/

[DONE] HTML/script injection audit (25/07/2026) - checked every single
       innerHTML/.setContent() call site across all three pages (~20
       locations). Every user-submitted field (name, location,
       description, links, gallery labels, other-photographers' names in
       the proximity-conflict warning) is correctly wrapped in
       escapeHtml() everywhere it's rendered. Remaining unescaped
       interpolations are all safe by construction (numeric coordinates,
       computed dates, hardcoded strings never fed by user input) or use
       .textContent/.setAttribute() instead of innerHTML. Zero real
       findings - genuinely clean.
[ ]    Date/time edge cases: end time before start time (client-side
       check exists - confirm server-side app-script.gs also rejects it,
       not just trusts the client)
[ ]    Coordinates right at the UK_BOUNDS edge (client validates, server
       validates - confirm both use the exact same box, still in sync)
[DONE] Google Sheets formula injection (25/07/2026) - the site already
       has a sanitizeForCell() helper (leading apostrophe forces plain-
       text if a value starts with =/+/-/@) applied consistently at
       nearly every write site. Found ONE real gap: confirmSignup()'s
       photographers.appendRow() copied name/website/email straight from
       the already-sanitized Signups row without re-applying
       sanitizeForCell() to the NEW row - Sheets' plain-text marker
       doesn't carry over on a fresh cell write, so this was a real,
       exploitable second-order gap. Fixed in app-script.gs, redeployed,
       and verified end-to-end via a real signup: submitted "=1+1 Test"
       as a photographer name through become-photographer.html, confirmed
       via the real email link, and the resulting Photographers row shows
       the literal text '=1+1 Test rather than evaluating to 2. Confirmed
       working - test row should be deleted from the Photographers sheet.
[DONE] Client-side form validation (25/07/2026) - verified empirically,
       not just read from code: invalid email format and empty required
       fields both correctly block submission (0 network requests fired,
       browser's own native validation message shown); maxlength
       correctly caps long input (tried 500 chars into an 80-char field,
       held at 80); a genuinely valid submission fires exactly 1 request.
       Raw HTML/script payloads in the name field ARE sent to the backend
       as-is (expected/correct - sanitization belongs at output/render
       time, already verified solid, not at submission time, which can
       always be bypassed by calling the API directly anyway).

NOTES
=============================================================================
- Several apparent bugs during this session's testing turned out to be
  test-harness artifacts once re-verified cleanly (bad click coordinates
  landing on an overlapping element, stale cached positions after the
  page moved, a recurring Playwright .click() vs raw-mouse-event quirk,
  unrelated background requests miscounted as duplicates). Worth staying
  skeptical of a first "failing" result and re-testing under cleaner
  conditions before treating it as real.
- device-tests.py is the permanent regression suite - anything confirmed
  as a real bug and fixed should get a permanent check added there,
  matching the pattern already established.
