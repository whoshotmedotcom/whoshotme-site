2. FORM VALIDATION & BOUNDARY CASES
=============================================================================
[DONE] Required-field validation on every form (25/07/2026) - click-
       tested systematically across add-shoot.html's shoot form (empty
       location, no pin dropped, end<=start, pin outside the UK - each
       blocked with a clear error and zero network requests fired) and
       profile form (empty name blocked, no request fired). Exactly one
       request fires on a genuinely valid submission in each case.
[DONE] Invalid formats: email (25/07/2026) - add-shoot.html's email-
       change field correctly rejects "not-an-email", "missing@dot",
       "@nodomain.com", "spaced out@example.com", and empty, with zero
       network requests fired for any of them; a valid address fires
       exactly one request. (Garbage URLs in website/logo fields not
       covered here - see note below.)
[DONE] Boundary values: very long names (25/07/2026). Found and fixed a
       real bug: a submitted name with no spaces (a run-on string,
       garbage input, a pasted hashtag) had nowhere to wrap in
       .resultItem (shared by the list view panel AND search results) -
       confirmed a 200-char unbroken name overflowing to ~1800px inside
       a ~360px box on a narrow mobile viewport. Fixed with
       overflow-wrap:break-word on .resultItem. Also hardened the map
       popup's .popup-name, which sits in a flex row (.popup-header)
       with no min-width:0 - it wasn't visibly broken (the popup grew to
       fit rather than overflowing), but was silently ignoring its own
       240px maxWidth to do so; added min-width:0 + overflow-wrap so it
       genuinely wraps within the intended width instead.
[DONE] Special characters / emoji (25/07/2026). Found and fixed a
       SEVERE bug: a photographer name starting with an emoji or any
       other character outside the Basic Multilingual Plane (stored as
       a UTF-16 surrogate pair) crashed the ENTIRE public map for EVERY
       visitor, not just that one row. Root cause: getInitials()'s
       `w[0]` grabbed the first UTF-16 code UNIT of a word rather than
       the first code POINT, splitting the surrogate pair in half. That
       lone surrogate then hit avatarFor()'s encodeURIComponent() call
       and threw "URI malformed" - and because this runs inside
       buildSpots()'s per-row .map() (after validateSpot() had already
       accepted the row as valid - a name existing is fine), the
       exception propagated all the way up and killed the whole data
       load, so the page showed "Couldn't load the map" for everyone.
       Fixed by spreading the string ([...w][0]) to iterate by code
       point instead of code unit. Verified: emoji, accented characters,
       &/<>/quotes, and em-dashes all render exactly as submitted (no
       double-escaping) in popups, list view, and search results, and
       accented-character search ("Café") works correctly.
[DONE] HTML/script injection audit (25/07/2026) - checked every single
       innerHTML/.setContent() call site across all three pages (~20
       locations). Every user-submitted field (name, location,
       description, links, gallery labels, other-photographers' names in
       the proximity-conflict warning) is correctly wrapped in
       escapeHtml() everywhere it's rendered. Remaining unescaped
       interpolations are all safe by construction (numeric coordinates,
       computed dates, hardcoded strings never fed by user input) or use
       .textContent/.setAttribute() instead of innerHTML. Zero real
       findings - genuinely clean.
[DONE] Date/time edge cases: end time before start time (25/07/2026) -
       confirmed both client (add-shoot.html) AND server (app-script.gs's
       validateShoot()) independently reject end<=start via a direct
       string comparison of the "YYYY-MM-DD HH:MM" format. Not just
       trusting the client.
[DONE] Coordinates at the UK_BOUNDS edge (25/07/2026) - confirmed
       app-script.gs's validateShoot() uses the exact same box
       (49.5,-10.9 to 61.2,2.1) as add-shoot.html's UK_BOUNDS, with an
       explicit comment tying the two together. Still in sync.
[DONE] Google Sheets formula injection (25/07/2026) - the site already
       has a sanitizeForCell() helper (leading apostrophe forces plain-
       text if a value starts with =/+/-/@) applied consistently at
       nearly every write site. Found ONE real gap: confirmSignup()'s
       photographers.appendRow() copied name/website/email straight from
       the already-sanitized Signups row without re-applying
       sanitizeForCell() to the NEW row - Sheets' plain-text marker
       doesn't carry over on a fresh cell write, so this was a real,
       exploitable second-order gap. Fixed in app-script.gs, redeployed,
       and verified end-to-end via a real signup: submitted "=1+1 Test"
       as a photographer name through become-photographer.html, confirmed
       via the real email link, and the resulting Photographers row shows
       the literal text '=1+1 Test rather than evaluating to 2. Confirmed
       working - test row should be deleted from the Photographers sheet.
[DONE] Client-side form validation (25/07/2026) - verified empirically,
       not just read from code: invalid email format and empty required
       fields both correctly block submission (0 network requests fired,
       browser's own native validation message shown); maxlength
       correctly caps long input (tried 500 chars into an 80-char field,
       held at 80); a genuinely valid submission fires exactly 1 request.
       Raw HTML/script payloads in the name field ARE sent to the backend
       as-is (expected/correct - sanitization belongs at output/render
       time, already verified solid, not at submission time, which can
       always be bypassed by calling the API directly anyway).

3. DOUBLE-SUBMIT / RACE PROTECTION
=============================================================================
[DONE] All 8 save/submit buttons across add-shoot.html and
       become-photographer.html - verified the disable-before-await
       pattern is consistently applied and actually works under a real
       in-flight-request race, not just present in the code
[PARTIAL] Two browser tabs open to the same dashboard (25/07/2026) -
       confirmed via testing: yes, this silently overwrites with no
       warning. Tab A saves a location change; Tab B (opened earlier,
       never reloaded) then saves its own description change and its
       stale copy of the location field silently reverts Tab A's edit,
       with no error or warning to either tab. Root cause: updateShoot()
       does a full-row overwrite of every field the form holds, with no
       version/timestamp check (LockService only prevents two
       *simultaneous* writes from corrupting each other, it doesn't
       detect a *stale* one). NOT fixed - this is a real architectural
       gap (would need a version/last-modified check to fix properly,
       not a small change), left as a known limitation rather than
       built out unprompted. Practical risk is low given the single-
       photographer usage pattern (same person on two devices at once
       editing the identical shoot is rare), but worth knowing about.

[DONE] Touch target sizes on mobile (25/07/2026) - originally measured

       Follow-up round (same day) after the site owner asked about
       remaining gaps: the popup close button (Leaflet's untouched
       24x24 default) and the About modal's close buttons (32x32
       circle, ~38px text button) hadn't been covered - fixed to 44px
       where practical (About modal, both buttons, all 3 pages) and to
       32x32 for the popup close button specifically (not the full
       44px - that would eat ~18% of this popup's own 240px maxWidth;
       32px is the best real improvement that fits without a larger
       popup redesign). "Get listed", the banner buttons, and "Back to
       today" also bumped to 44px. The plain-text "About" link (not a
       button visually) got a bigger invisible tap zone via padding +
       matching negative margin instead of a visual resize, since
       growing it to look like a button would clash with the sentence
       it sits in.

       This round of resizing surfaced 3 REAL, confirmed bugs from the
       combined-control/bigger-button changes, all found via testing on
       a real iPhone 14 viewport (not just synthetic desktop sizes) and
       all fixed:
       - Popups could render underneath the bottom-left control stack -
         two compounding causes: Leaflet's cached map size was stale
         (~50px taller than the map's true height, measured before the
         page's real layout had settled - fixed with an explicit
         map.invalidateSize() once initial load completes), and the
         3-row control stack itself left too little room even with
         correct math (fixed by combining Reset view + My location into
         one row, cutting the stack from ~206px to ~152px). Popup
         maxHeight is now also computed dynamically from the map's
         actual current size rather than a fixed 320px guess.
       - Aerial's attribution (3 stacked layers each contributing their
         own credit string) wrapped to 2 lines wide enough to reach the
         zoom control despite being anchored bottom-right - fixed by
         attributing the group once instead of 3 times, and capping the
         attribution box's width so it can't grow that wide regardless.
       - Popups could open underneath the search bar specifically while
         the location-consent/photographer-filter banner was showing
         (fixed top-left padding didn't account for the banner pushing
         the search box down) - fixed by measuring the search box's
         real current position. Testing this surfaced a genuinely
         separate pre-existing race: flyToSpot() closed the search
         dropdown as the LAST line of the function (too late if
         setView() resolves synchronously) and a debounced place-search
         lookup could re-show the dropdown after a result was already
         selected - both fixed.

       Full device-tests.py suite (76/76, up from 64) and repeated real-
       viewport testing confirmed no remaining overlap or layout
       breakage. See git log 25/07/2026 for full detail on each.
